A build week makes an idea answer questions that a planning document can postpone. Can the central interaction be expressed clearly? Is there enough material to test? Does using the prototype create a better question than the one that started it?

I made three small prototypes during a recent week. None became a finished product. Two were still useful.

## The constraint

Each prototype had one day to reach a testable state. “Testable” meant that I could use the main loop with real input. Visual completeness and edge cases came later, if the loop earned more time.

```ts
type Prototype = {
  question: string;
  mainLoop: string;
  evidenceByFriday: string;
};
```

Writing those three fields before starting made the week much less ambiguous.

## What survived

The most useful prototype had the least interface. It converted a weekly note into a short review and placed the previous week beside it. The side-by-side view revealed repeated blockers that individual entries hid.

Another prototype failed as a product but produced a useful rule: a planning tool should reduce the number of states a task can occupy. The prototype had added states to make the system feel precise. In use, they only created more classification work.

## What did not

One idea never reached its central loop because I spent too long designing its data model. The model handled future cases that the prototype did not yet contain. By the time the first real input was available, there was not enough time left to learn from it.

The lesson was not “never plan.” It was to plan around the evidence the week is meant to produce.

## Next time

I will keep the one-day limit and add a stricter checkpoint at noon: the prototype must accept one piece of real input by then. If it cannot, the scope changes before more infrastructure is added.

The durable output of a build week is not a pile of demos. It is a smaller set of ideas that have been forced to reveal their next question.
